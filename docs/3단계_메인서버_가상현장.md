# 3단계 · 규칙 기반 메인 서버와 가상 리치스태커

메인 서버가 **보조 키트에는 센싱을, 리치스태커에는 이동·하강·결합을 지시**하는 전체 흐름을 시뮬레이션으로 완성한 단계입니다.
메인 서버의 판단은 **규칙 기반(같은 입력이면 항상 같은 결정)** 이고, 언어 AI는 운영자 비서로만 붙일 수 있습니다(6절).

## 1. 구성

| 구성 | 파일 | 하는 일 |
|---|---|---|
| 메인 서버 판단 | `app/main_controller.py` | 코너별 추정 종합, 기존 센서와 우선순위, 하강 인터록 |
| 가상 리치스태커 | `app/reachstacker_sim.py` | 접근, 보정 이동(구동 오차 포함), 하강, 결합, 상승, 기존 센서(정상·불안정·없음·편향), 키트 코너 고장 주입 |
| 가상 현장(실시간) | `app/sim_site.py` | 위 둘을 묶어 키트와 메시지로 주고받음. 내장 서버와 예제 서버가 같은 코드를 씀 |
| 연결 | `app/sim_bridge.py` | 서버 미설정이면 프로그램 안에서, 설정이면 예제 서버의 가상 현장을 사용 |
| 일괄 실행 | `app/sim_job.py` | 같은 단계를 한 번에 돌려 비교 실험·테스트에 사용 |
| 비교 실험 | `app/tools/compare_strategies.py` | 아래 5절 표 생성 |
| AI 운영 비서(선택) | `app/tools/ai_operator.py` | Ollama 로컬 모델, 허용 명령만 |

키트는 1단계 그대로입니다. 가상 현장에서도 키트는 명령을 받고 묶음을 보낼 뿐이며, 장치 쪽 계산(`kit_device.py`)도 같습니다.

## 2. 작업 순서 (가상 현장)

1. **접근**: 원거리에서 받은 컨테이너 대략 위치로 리치스태커가 이동
2. **센싱 범위 진입**: 기계 자체 센서로 키트 범위(Maxwell 데이터 ±30 mm) 안에 들어오면 메인 서버가 키트에 `start_job`
3. **센싱 → 판단 → 보정 이동** 반복 (최대 6회)
4. **하강 조건 확인** → 하강 → 결합(네 코너 모두 5 mm 이내일 때만 잠김) → 상승 → 키트에 `end_job`
5. 조건이 안 맞으면 **하강하지 않고 안전 정지**(`stop`)

> 대략 위치(보통 m 단위)에서 ±30 mm 안으로 들어오는 것은 리치스태커의 기존 센서·운전자 몫으로 가정합니다. 범위 밖에서 센싱하면 키트가 외삽 표시와 낮은 신뢰도로 알려 줍니다.

## 3. 메인 서버 판단 규칙

### 3-1. 4코너 종합

| 방식 | 내용 |
|---|---|
| v3.5.4 그대로 | 4코너 동일 가중, 인터록 없음 (기존 결과 재현용) |
| 4코너 동일 가중 | 위와 같되 인터록 사용 |
| 고정 기준 (대각선) | 코너 1·3만 사용 (회전 정밀도가 가장 좋은 대각선 쌍) |
| **신뢰도 가중 + 튀는 코너 제외** (기본) | 양호 1.0 / 주의 0.7 / 무효 0. 강체 맞춤 잔차가 12 mm를 넘는 코너 하나를 빼고 다시 맞춤 |

맞춤은 가중 최소제곱 강체 이동(X, Y, 회전)입니다. 4코너·동일 가중이면 v3.5.4 계산과 똑같습니다.
남은 코너가 1개면 이동만 보정하고 회전은 보정하지 않습니다.

### 3-2. 기존 센서와 우선순위 (팀 설계 5가지 상황)

| 상황 | 조건 | 기존 센서 : 키트 |
|---|---|---|
| P1 정상 | 기존 센서 정상 + 키트 양호 | 0.7 : 0.3 (키트는 교차 검증) |
| P2 기존 센서 불안정 | 기존 센서 불안정 + 키트 양호 | 0.2 : 0.8 |
| P3 기존 센서 정보 없음 | 키트 사용 가능 | 0 : 1 |
| P4 단독 판단 불충분 | 키트 '주의' (기존 센서 정상 또는 불안정) | 0.5 : 0.5 |
| P5 둘 다 신뢰도 부족 | 키트 무효 + 기존 센서 정상 아님 | 보정 보류 → 재측정 2회 → 안전 정지 |

키트 종합 상태: 쓸 수 있는 코너 3개 이상이 '양호'이고 맞춤 잔차 4 mm 이하면 **양호**, 2개 이상이면 **주의**, 그 외 **무효**.

**두 센서가 다를 때**: 차이가 6 mm + 현재 오차의 30%를 넘으면 먼저 재측정합니다. 그래도 다르면
- 키트가 스스로 일관되면(양호) → **키트 채택**, 기존 센서 의심
- 키트가 불확실하고 기존 센서가 정상이라고 하면 → **기존 센서 채택**
- 둘 다 아니면 → **안전 정지**

### 3-3. 하강 인터록 (무조건적 보정·하강 방지)

- 키트가 본 네 코너가 모두 1 mm 이내일 때만 하강합니다. 기존 센서를 섞는 경우에는, 섞은 오차가 1 mm 이내이고 이동 후 예상 최악 코너가 4 mm 이하여야 합니다.
- 6회 안에 조건을 못 맞추면 마지막 이동 뒤 **최종 확인 센싱**을 한 번 합니다. 예상 최악 코너가 4 mm 이하면 하강하고, 아니면 하강하지 않고 정지합니다.
- 결합 허용 오차는 5 mm(v3.5.4 판정과 같음)이고, 인터록 기준 4 mm는 1 mm 여유를 둔 값입니다.

### 핵심 결과

1. **인터록이 위험한 하강을 크게 줄입니다.** 기준 가정에서 v3.5.4 방식은 37.7%가 5 mm 밖에서 하강했어요. 인터록을 쓰면 6~8%로 줄고, 대신 약 절반은 하강하지 않고 멈춥니다. 기준 가정 하드웨어는 자동 결합에 쓰기엔 부족하다는 뜻이고, 시스템이 그걸 알아차리고 멈추는 것이 맞는 동작이에요.
2. **목표 하드웨어에서는 신뢰도 가중 + 튀는 코너 제외가 가장 안정적이에요.** 코너 하나의 헤드 2개가 고장 나도 성공 100%, 잘못된 하강 0%입니다. 같은 고장에서 다른 방식은 이렇게 나빠져요.
   - 동일 가중: 약 30%가 정지
   - v3.5.4: 9~10%가 잘못 하강
   - 고정 기준(대각선): 고장이 기준 코너에 생기면 20%가 잘못 하강
3. **고정 기준 코너 방식은 권하지 않아요.** 고장이 기준 쌍 밖(코너2)이면 완벽하지만, 기준 코너(코너1)가 고장 나면 가장 나쁘고, 기준 가정에서는 66%가 잘못 하강합니다. 장치 4대 중 하나를 고정 기준으로 두는 대신 회차마다 신뢰도로 정하는 편이 안전해요.
4. **교정 틀어짐(장치가 스스로 모르는 고장)** 은 목표 하드웨어에서 어느 방식이든 거의 영향이 없었어요. 가정한 틀어짐 크기(헤드 2개에 약 2 μH)가 이력 추정이 흡수할 수 있는 수준이었기 때문입니다.
5. **기존 센서 우선(P1, 0.7:0.3)은 목표 하드웨어에서 키트 단독보다 성공률이 낮아요** (94.3% 대 99.7%). 다만 잘못된 하강은 없었어요. 가정한 기존 센서(잡음 1.5 mm, 편향 1 mm)가 이 범위에서는 키트보다 덜 정밀해서, 마지막 수 mm는 키트가 더 잘 맞춥니다. **제안**: 먼 거리 접근은 기존 센서 우선, 센싱 범위 안의 마지막 보정은 키트 우선으로 단계별 가중치를 두는 방식. 팀 설계(정상 시 기존 센서 우선)를 바꾸는 일이라 반영하지 않고 제안으로만 남깁니다.
6. **기존 센서가 불안정하거나 몰래 틀어져도 잘못된 하강은 0%** 였어요(목표 하드웨어). 불일치를 감지해 재측정하고, 일관된 키트를 채택하거나 멈췄기 때문입니다.
7. **약점**: 기준 가정에서 한 코너가 고장 나면 신뢰도 가중 방식의 잘못된 하강이 28~29%로 올라가요. 남은 3코너의 모델 편차를 가려내지 못하기 때문입니다. 하드웨어를 목표 사양으로 올리는 것이 근본 대책입니다.

## 6. AI 운영 비서 (선택, 무료)

`app/tools/ai_operator.py` 는 [Ollama](https://ollama.com) 로 PC에서 돌리는 공개 모델(예: `qwen2.5:7b`)을 운영자 비서로 씁니다. 인터넷이 필요 없고 사용 한도도 없습니다.

```
ollama pull qwen2.5:7b
python app/server_example/malign_main_server.py --port 8750
python app/tools/ai_operator.py --server http://127.0.0.1:8750 "KIT-0001로 가상 작업 하나 시작해줘"
```

- 쓸 수 있는 명령: 작업 목록, 키트 상태, 가상 작업 시작, 기계 준비 완료, 키트에 정지·자가 점검·이상 해제.
- 보정·센싱·하강·작업 종료는 **쓸 수 없습니다**. 그 판단은 규칙 기반 제어기가 합니다.
- 실제 모델 연결은 이 개발 환경에서 시험하지 못했습니다. 명령 연결과 금지 명령 차단은 가짜 모델로 시험했습니다(`tests/test_ai_operator.py`).

## 7. 한계

- 모든 결과는 FEM 기반 가상 시뮬레이션입니다. 리치스태커 기존 센서 모델(잡음 1.5 mm, 편향 1 mm 등)과 고장 모델은 가정값입니다.
- 우선순위 가중치(0.7/0.3 등)는 팀 설계를 그대로 옮긴 값이며 최적화하지 않았습니다. 신뢰도 가중(주의 0.7)과 튀는 코너 기준(12 mm)만 실험으로 골랐습니다.
- 원거리 접근 단계는 "센싱 범위 안으로 들어왔다"는 결과만 흉내 냅니다.
- 2단계(Modbus TCP)는 아직 하지 않았습니다. 현재 전달 방식은 HTTP입니다.
